# Healthcare Appointment & Follow-up Manager

A simple web application for managing clinic appointments.

The project has three types of users:

- **Admin** – manages doctors, working hours, slot duration, and leave days.
- **Doctor** – views appointments and adds notes and prescriptions.
- **Patient** – registers, searches for doctors, books appointments, and views appointment history.

The application also includes:

- Pre-visit and post-visit AI summaries
- Protection against double-booking
- Doctor leave handling
- Email notifications
- Calendar event files
- Medication reminder handling

The project is designed to run locally without setting up a separate database, email account, or Google Cloud project.

---

## 1. Requirements

Install these before running the project:

- **Node.js**
- **npm**
- A web browser such as Chrome or Edge
- VS Code is recommended, but any code editor can be used

You can check Node.js and npm from a terminal:

```bash
node --version
npm --version
```

---

## 2. Download and open the project

Download or clone the repository and open the project folder in VS Code.

Open the VS Code terminal:

**VS Code → Terminal → New Terminal**

Make sure the terminal is inside the project folder.

You can check the current folder with:

```bash
cd
```

On Windows PowerShell, you can also use:

```powershell
Get-Location
```

---

## 3. Install the project

Run this in the **VS Code terminal**, from the project folder:

```bash
npm install
```

This installs the packages required by the application.

You only need to run `npm install` again if the dependencies change or if you remove the `node_modules` folder.

---

## 4. Start the application

Run:

```bash
npm start
```

The server should start on:

**http://localhost:3000**

Open that address in your browser.

Keep the terminal running while you use the application.

To stop the server, press:

```text
Ctrl + C
```

in the terminal.

## 6. Recommended demo flow

The easiest way to test the complete project is to use the three roles in this order.

### Step 1 – Admin

Log in with:

```text
Email: admin@clinic.local
Password: admin123
```

From the Admin portal you can:

- Add doctors
- Set doctor specialisation
- Set working hours
- Set appointment slot duration
- Mark a doctor as unavailable for a particular date

A leave day will also handle any booked appointments for that doctor on that date.

---

### Step 2 – Patient

Log out of the admin account and create a patient account.

Then:

1. Search for a doctor by specialisation.
2. Select a date.
3. View the available appointment slots.
4. Enter the patient's symptoms.
5. Confirm the appointment.

When the booking is created, the system can generate a pre-visit summary and create notification/calendar data.

---

### Step 3 – Doctor

Log in using one of the doctor accounts.

The doctor can:

- View appointments
- Read the pre-visit summary
- Add visit notes
- Add a prescription
- Complete the appointment

After an appointment is completed, the patient receives a post-visit summary.

## 8. Email notifications

By default, email sending is kept local so the project can be tested without a real email account.

Notifications are written to:

```text
data/emails.log
```

You can open this file to check messages generated by the application.

Examples include:

- Booking confirmations
- Appointment cancellations
- Post-visit summaries
- Medication reminders

A real email provider can be connected later by changing the email service configuration.

---

## 9. Calendar events

The project creates `.ics` calendar files instead of requiring a live Google Calendar connection.

The files are stored in:

```text
calendar_events/
```

An `.ics` file can be opened or imported into calendar applications such as:

- Google Calendar
- Microsoft Outlook
- Apple Calendar

This keeps the project easy to run locally.

---

## 10. What happens when a doctor is put on leave?

When the admin marks a doctor as being on leave:

1. The system finds booked appointments for that doctor on that date.
2. Those appointments are cancelled.
3. The related calendar files are removed.
4. The affected patients receive a cancellation notification.
5. Patients can book another appointment.

---

## 11. Double-booking protection

The application checks whether a doctor already has a booking for a selected date and time.

If the slot is already booked, another patient cannot successfully book the same slot.

This is handled before the appointment is saved, so the main booking is completed before slower tasks such as AI summaries, email processing, or calendar file creation.

## 12. Project structure

The main files and folders are:

```text
server.js
src/
├── db.js
├── seed.js
├── middleware/
│   └── auth.js
├── routes/
│   ├── authRoutes.js
│   ├── adminRoutes.js
│   ├── patientRoutes.js
│   └── doctorRoutes.js
├── services/
│   ├── llmService.js
│   ├── emailService.js
│   ├── calendarService.js
│   └── reminderJob.js
└── utils/
    ├── password.js
    └── slotUtils.js

public/
data/
calendar_events/
package.json
package-lock.json
```

### Main purpose of the files

**`server.js`**  
Starts the Express server and connects the application parts.

**`src/db.js`**  
Handles the local JSON data store.

**`src/seed.js`**  
Creates the initial demo admin and doctor accounts.

**`src/routes/`**  
Contains the main API routes for login, admin actions, patient actions, and doctor actions.

**`src/services/llmService.js`**  
Handles the AI summaries and the local fallback.

**`src/services/emailService.js`**  
Handles notification creation and email logging.

**`src/services/calendarService.js`**  
Creates calendar event files.

**`src/services/reminderJob.js`**  
Handles background notification retries and medication reminders.

**`public/`**  
Contains the browser-side HTML, CSS, and JavaScript for the portals.

**`data/`**  
Stores application data created while the server is running.

## 13. Local data files

The application uses local files instead of a separate database server.

### `data/db.json`

This stores application data such as:

- Users
- Doctors
- Appointments
- Notifications

The file is created when the application starts.

### `data/emails.log`

This stores the notifications generated by the application when local email mode is being used.

### `calendar_events/`

This stores the generated `.ics` calendar files.

These files are useful when demonstrating the project because you can see the data created by the application directly.

Stop the server first with:

```text
Ctrl + C
```

Then remove the generated local data files/folders:

```text
data/db.json
data/emails.log
calendar_events/*.ics
```

Start the application again:


## 16. Common problems

### `npm` is not recognized

Node.js is probably not installed correctly.

Install Node.js, restart VS Code, and check:

```bash
node --version
npm --version
```

### `npm start` does not work

Make sure:

- You are in the project folder.
- `npm install` has completed.
- `package.json` is present.

Then run:

```bash
npm start
```

### The browser cannot open `localhost:3000`

Check the terminal.

The server must still be running. If it stopped, start it again:

```bash
npm start
```

Then open:

```text
http://localhost:3000
```

### No email was received

That is expected in the default local setup.

Check:

```text
data/emails.log
```

The project records the generated notifications there instead of sending real email.

## 17. Simplifications in this project

This is a learning/demo project, so a few parts are intentionally kept simple.

### Database

The project uses a JSON file instead of PostgreSQL, MySQL, or MongoDB.

This means you can start the project without installing a database server.

### Login sessions

Sessions are kept in application memory, so this setup is intended for a local single-server demo.

### Email

Email notifications are logged locally by default instead of being sent through a real email provider.

### Calendar

The project creates `.ics` calendar files instead of connecting directly to Google Calendar.

### Background tasks

Reminder and retry tasks run inside the Node.js application rather than using a separate job server.

These choices make the project easier to install, understand, and demonstrate.
